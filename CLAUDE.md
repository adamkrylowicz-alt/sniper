# Sniper — Trading 212 Panel

## Stack
- Backend: Python (lokalnie 3.11, na NAS-ie faktycznie 3.8), Flask (application factory pattern)
- Frontend: HTML/JS/CSS (Jinja2 templates)
- Baza: SQLite (instance/sniper.db)
- Deploy: Synology NAS, **goły proces `python3 run.py`** (NIE Docker — `docker` nie ma nawet na PATH w SSH), port 5050, dostęp w LAN przez http://192.168.1.50:5050. Od 19.07.2026 też publicznie przez **https://snajper.duckdns.org** (nginx-proxy-manager jako reverse proxy + Let's Encrypt + warstwa HTTP Basic Auth PRZED logowaniem appki). Produkcyjnie serwowane przez `waitress` (nie wbudowany dev-server Flaska) — **brak auto-reloadu**, po każdym uploadzie appka wymaga RĘCZNEGO restartu (`pkill -9 -f run.py`, potem `nohup python3 run.py > /tmp/sniper_start.log 2>&1 &`)
- Upload: `t212-panel/upload_sniper.ps1` (SCP/PowerShell) — UWAGA: jest też stary, nieaktualny `pliki/upload_sniper.ps1` z innej maszyny, nie używać
- **WAŻNE — prod to WYŁĄCZNIE cel deployu**: `/volume1/docker/t212-panel` na NAS-ie NIGDY nie edytować bezpośrednio (ręcznie przez SSH ani przez sesję Claude Code odpaloną w tym folderze). Cała edycja kodu idzie przez lokalne repo (ten komputer) albo przez `/volume1/docker/t212-panel-dev` (osobny, git-tracked klon do zdalnego kodowania z NAS-a) → commit + push → dopiero wtedy `upload_sniper.ps1` na prod. Jeśli kiedyś jednak trzeba zrobić hotfix wprost na prodzie, tego samego dnia wrócić zmianę do gita (skopiować plik do repo, commit) — inaczej kolejny upload cicho nadpisze hotfix i powstaje trwały, niewidoczny rozjazd między tym co realnie działa a tym co jest w repo (wykryte 2026-07-21: `bot_engine.py` na prodzie miał logikę nieobecną w repo/dev-klonie).

## Struktura
- `t212-panel/run.py` — punkt wejścia; respektuje `Config.DEBUG` (domyślnie False) — lokalnie z `FLASK_DEBUG=true` w `.env` leci `app.run(debug=True)`, produkcyjnie `waitress.serve()`
- `t212-panel/app/__init__.py` — fabryka aplikacji (`create_app()`), rejestracja blueprintów, `ProxyFix` (żeby `request.is_secure`/`remote_addr` widziały prawdziwego klienta przez nginx-proxy-manager), scheduler, root `/` redirect
- `t212-panel/app/routes/*.py` — blueprinty: auth, scalping (Warp+Focus), settings, api_keys, report, pie, bot, instrument
- `t212-panel/app/services/*.py` — logika: t212_client, instrument_cache, logo_cache, risk_guard, session_store, bot_engine, price_feed, finnhub_client, mailer
- `t212-panel/app/templates/`, `t212-panel/app/static/` — HTML/JS/CSS
- `t212-panel/migrate_add_*.py` — jednorazowe, idempotentne migracje SQLite (ALTER TABLE) — uruchamiane ręcznie po uploadzie, bo `db.create_all()` nie dokłada kolumn do istniejących tabel

## Ważne konteksty
- **Strefy czasowe**: Adam mieszka koło Amsterdamu (CEST latem = UTC+2, CET zimą = UTC+1) - domyślnie zakładaj TĘ strefę jako "która jest teraz godzina" przy dowolnym pytaniu wrażliwym na czas (nie tylko przy analizie bota), chyba że Adam wyraźnie powie że jest gdzieś indziej. WSZYSTKIE znaczniki czasu w bazie (`bot_audit_log.created_at`, `ActiveTrade.created_at` itd.) są w **UTC** (`dt.datetime.utcnow()` w kodzie) - NIE lokalny czas Adama, więc przy ich odczycie zawsze przeliczaj na Amsterdam. Ma to znaczenie przy ocenie czy giełda jest otwarta: Euronext Amsterdam/Xetra Frankfurt (spółki `*a_EQ`/`*d_EQ`, EUR) handlują ~9:00-17:30 CEST, NASDAQ/NYSE (`*_US_EQ`, USD) ~15:30-22:00 CEST latem (obie strefy DST przesuwają się w różnych terminach, więc offset USA vs Europa nie zawsze jest stały cały rok) - zlecenie LIMIT BUY złożone po zamknięciu europejskiej giełdy realnie ruszy dopiero następnego dnia handlowego, to nie błąd bota, tylko normalne zamknięcie rynku.
- T212 API: rate limity na demo są bardzo restrykcyjne, niektóre endpointy zwracają 403 na demo
- Zero-Knowledge encryption na auth (cipher.py) — master_key nigdy nie trafia do bazy w formie jawnej
- Warp Mode = one-click trading grid (siatka 3x3)
- Focus Mode = karuzela dużych kafelków z ceną live/sparkline z Finnhub (dodane 17.07.2026)
- Smart Virtual Pie = "wirtualne ETF-y" (koszyki instrumentów z proporcjonalnymi wagami)
- Micro-Grid Bot = automatyczny bot działający na APScheduler (tick co 60s), patrz `extensions.py::scheduler`
- Ceny/wykresy: Finnhub (klucz `FINNHUB_API_KEY`) jako główne źródło, Yahoo Finance jako fallback dla bota
- Logotypy spółek: Logo.dev (`LOGO_DEV_API_KEY`) — Clearbit jest MARTWE od grudnia 2025, nie wracać do niego
- Strona szczegółów instrumentu (`/instrument/<ticker>`, `routes/instrument.py`) — wspólny cel kliknięcia w logo/nazwę aktywa z Warp/Focus/Watchlist/Pie/Bota; wykres świecowy z zakładkami 1T/1M/3M/1R/MAX, Kup/Sprzedaj, "Twoja inwestycja"
- Rejestracja (`/auth/register`) jest publiczna, ale konto wymaga DWÓCH bramek zanim się zaloguje: klik w link aktywacyjny z maila (`User.email_verified`) + ręczne zatwierdzenie admina w Ustawienia → Oczekujące konta (`User.is_active`). Pierwszy user w bazie = admin automatycznie (`User.is_admin`)
- Strona "Aktywa" (`/warp/portfolio`) — wszystkie otwarte pozycje z T212, ładuje się z cache (`scalping.py::_portfolio_cache`, w pamięci procesu), świeży odczyt dociąga `portfolio.js` z opóźnieniem w tle (znacznik czerwony "Z cache" / zielony "Aktualne" pod wartością portfela)
- Wykresy dla instrumentów spoza giełd USA (głównie europejskich) — `services/yahoo_resolver.py` automatycznie i leniwie znajduje symbol Yahoo Finance przy pierwszym użyciu tickera (dopasowanie po walucie, wynik cache'owany na stałe w `YahooSymbolMap`), zamiast wymagać ręcznego wpisu do `finnhub_client.py::TICKER_MAP`
- Marka appki to teraz **SNAJPER** (nie SNIPER) we wszystkich miejscach widocznych dla użytkownika — zmienione 19.07.2026, zostały tylko 2 wewnętrzne docstringi (cipher.py/models.py)
